NEW EARLY STOPPING IN FINETUNING:
-------------------------------
Fine-tuning improvements to port from crypto.ai → gorm.ai

  Both projects share the same fine-tuning architecture (it was copied), so file/function names should match. Package root differs (crypto_ai → your gorm_ai). The flow is: UI
  (ai-models page, localStorage) → FinetuneRequest → FinetuneService.run_finetune → engine runner (_finetune_timesfm.py / _finetune_moirai2.py) → _train_outlet.

  There are two independent changes. Change 1 is small and high-value; Change 2 is a feature.

  Change 1 — Best-epoch checkpoint restore (+ a latent sane-check bug fix)

  Problem: _train_outlet saved whichever epoch it stopped on, not the best one. On noisy data the last epoch is often worse than an earlier one. Also, best_loss was only updated inside
  if patience > 0, so when early stopping was disabled (patience=0) the pathological sane-check saw best_loss = inf and could wrongly skip every series.

  Fix (in _train_outlet, both _finetune_timesfm.py and _finetune_moirai2.py):
  - Track best_loss and best_state every epoch (not gated on patience):
  if avg_loss < best_loss:
      best_loss = avg_loss
      best_state = copy.deepcopy(nn_module.state_dict())
      stale = 0
  else:
      stale += 1
  - After the epoch loop (early-stop OR full run), restore best:
  if best_state is not None:
      nn_module.load_state_dict(best_state)
  nn_module.eval()
  - Keep the existing pathological snapshot restore separate (it restores the pre-training weights on sane-check failure; best_state restores the best weights at the end).

  Change 2 — "Early Stopping Method" setting: training-loss vs. validation-set

  Goal: add a dropdown on the ai-models fine-tune tab (above "Early Stopping Patience") to choose how the best epoch is selected:
  - Training loss (patience) — existing behavior; stop when training loss hasn't improved for patience epochs.
  - Validation set (best epoch) — hold out the most-recent N% of each series' windows (never trained on), run all epochs, keep the epoch with the best validation loss. Generalization
  guard against overfitting. When this is selected, hide the patience field and show a "Validation Split (%)" field instead.

  Backend

  a) _SlidingWindowDataset (both runners): add a constructor to build from a pre-sliced window list:
  @classmethod
  def from_windows(cls, windows):
      obj = cls.__new__(cls)
      obj.windows = windows
      return obj

  b) Factor the forward/loss into reusable helpers so train and validation share one code path:
  - TimesFM: _forecast_batch(nn_module, ctx_batch, p, o, q, horizon) and _eval_avg_loss(nn_module, loader, p, o, q, horizon, device) (the latter wraps torch.no_grad() +
  nn_module.eval()).
  - MOIRAI-2: factor its branchy loss into _batch_loss(nn_module, ctx_batch, tgt_batch, context_length, horizon, device), plus an _eval_avg_loss using it.

  c) _train_outlet new params early_stopping_method: str = "training", validation_split: float = 0.0, and logic:
  full = _SlidingWindowDataset([series], ctx_len, horizon)
  if len(full) == 0: return False

  use_val = early_stopping_method == "validation" and 0.0 < validation_split < 1.0 and len(full) >= 2
  if use_val:
      n_val = max(1, int(round(len(full) * validation_split)))
      n_val = min(n_val, len(full) - 1)               # keep ≥1 training window
      train_ds = _SlidingWindowDataset.from_windows(full.windows[:-n_val])
      val_ds   = _SlidingWindowDataset.from_windows(full.windows[-n_val:])   # most-recent windows
  else:
      train_ds, val_ds = full, None
  # loaders: train shuffled, val not. val_loader = None when not use_val.
  Per epoch: train on train_ds; compute train_avg; if val_loader, val_avg = _eval_avg_loss(...). Then:
  - monitor = val_avg if use_val else train_avg
  - best-restore on monitor (deepcopy on improvement)
  - sane-check stays on training loss (track best_train = min(best_train, train_avg); its threshold is tuned for training MSE)
  - patience early-stop applies only when not use_val: if not use_val and patience > 0 and stale >= patience: break
  - net effect: validation method runs the full epoch budget and keeps the best-validation epoch (no patience).

  d) run_finetune signatures (both runners): add early_stopping_method: str = "training", validation_split: float = 0.0, and pass them into the _train_outlet call.

  e) FinetuneService.run_finetune: extract from request_data and pass to the runner:
  early_stopping_method = request_data.get("early_stopping_method", "training")
  validation_split = request_data.get("validation_split", 0.0)
  # ... runner(..., early_stopping_method=early_stopping_method, validation_split=validation_split)

  f) FinetuneRequest (route schema): add
  early_stopping_method: str = "training"   # "training" | "validation"
  validation_split: float = 0.0             # 0–1 fraction held out when method == "validation"

  ▎ ⚠️ If gorm's MOIRAI-2 run_finetune signature doesn't already accept sane_check_epochs/max_sane_loss, add them too (accepted-but-unused is fine) — the service passes them by keyword

  19. WIFUSDT

  DeFi
  20. UNIUSDT

  The reasoning was: BTC/ETH are the two most efficient, most-arbitraged markets in crypto, so net of fees their direction is ~random. Less-efficient mid-caps (#9–15) are where trends
  are most likely to persist long enough to be tradeable — so they're the best place to start. The meme names swing hard (good for a volatility signal) but are the easiest to overfit.

  And the two levers that matter more than the ticker:
  - Timeframe — 1h is the most efficient; try 4h / 1d where autocorrelation is higher.
  - Min predicted move — require the forecast to clear a real % move so fees don't eat the edge.

  This is exactly what the new Batch Runner is for: import a handful of these, then run one batch across all of them and look at the median excess vs buy & hold rather than any single
  coin. Want me to kick off the background imports for, say, the 7 mid-caps at 4h + 1d so you can batch them?
